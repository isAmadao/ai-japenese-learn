### 2026-07-07：迁移后端代码 + 修复 Vite 代理

#### 完成内容

- **`core/auth.py`** 重写：用 `AuthClient`（fastapi-auth-client）替代 `AuthKit`（fastapi-auth-kit），JWT 验证通过 auth-service 的 JWKS 公钥
- **自动创建本地 User**：首次登录时根据 JWT payload 自动创建本地用户记录，不破坏现有外键关系
- **`config.py`** 清理：去掉 `JWT_SECRET_KEY`/`SMTP`/`VERIFY_CODE` 等不再需要的配置，替换为 `AUTH_SERVICE_URL`
- **`database.py`** 清理：去掉 `seed_admin` 调用（auth-service 负责）
- **`main.py`** 清理：去掉 `auth_kit.initialize(app)`，移除废弃 import
- **`api/auth.py`** 删除：不再需要（login/register 由 auth-service 处理）
- **`requirements.txt`** 更新：`../auth-kit` → `fastapi-auth-client`
- **`test/conftest.py`** 更新：mock `get_current_user`/`require_admin` 依赖使测试通过
- **`vite.config.ts`** 更新：`/api/auth/*` 和 `/api/admin/users/*` 代理到 auth-service

**服务运行状态：**

| 服务 | 端口 | 状态 |
|------|------|------|
| auth-service | `:8080` | RS256 JWT 签发 + JWKS |
| backend | `:8000` | 业务 API |
| Vite | `:5173` | 前端开发服务器 |

#### 问题 & 解决方案

**问题1：Vite proxy 请求 401**

现象：直连 backend `127.0.0.1:8000` 验证成功，经 Vite proxy 后 401
根因：Windows 上 `localhost` 可能解析为 IPv6 `::1`，与绑定的 IPv4 `127.0.0.1` 不匹配
解决：`vite.config.ts` 中 target 全部改为 `http://127.0.0.1:xxxx`
效果：前端页面可正常访问业务 API

**问题2：pytest 返回 401（缺少 token）**

现象：迁移后测试全部失败，返回 401 Unauthorized
根因：`conftest.py` mock 了 DB 但没有 mock auth 依赖
解决：在 `conftest.py` 中通过 `app.dependency_overrides` 注入 fake user/admin
效果：21 个 auth 相关测试全部通过

**问题3：后台服务进程管理**

现象：bash 后台启动的 uvicorn 进程容易失联
根因：bash 环境缺少进程管理工具（无 tmux/screen）
解决：使用 `subprocess.Popen` 通过 Python 脚本统一管理，但脚本退出后子进程仍可能终止

### 2026-07-08：Docker 容器化部署 — 镜像瘦身 + auth-service 集成

#### 完成内容

- **镜像瘦身 70%**：9.42GB → **2.81GB**
  - 发现 `easyocr` → `torch` 在 Linux 上默认拉 CUDA 版（nvidia-* 包 ~2GB），容器运行只需 CPU
  - Dockerfile 策略：先装 CPU-only torch（`download.pytorch.org/whl/cpu`），再装 requirements.txt
  - 同时清理 `bcrypt`、`email-validator` 等不再需要的依赖
- **`fastapi-auth-client` 发布到 PyPI**：[pypi.org/project/fastapi-auth-client/0.1.0](https://pypi.org/project/fastapi-auth-client/0.1.0/)
- **auth-service Docker 化**：创建 Dockerfile，加入 docker-compose.yml，自动生成 RSA 密钥对 + JWKS 端点
- **nginx 配置更新**：`/api/auth/*` → `auth-service:8080`，`/api/admin/users` → `auth-service:8080`
- **Dockerfile 清理**：去掉 `COPY auth-kit/`（由 `fastapi-auth-client` PyPI 包替代）
- **nginx 端口屏蔽**：去掉 `app` 服务的 `8000:8000` 映射，强制用户通过 nginx（`:80`）访问

#### 服务架构（最终）

| 服务 | 镜像大小 | Docker 端口 | 说明 |
|------|:--------:|:-----------:|------|
| nginx | 93MB | :80 | 前端页面 + API 反向代理 |
| app | **2.81GB** | — | 日语学习 API（仅内网） |
| auth-service | ~330MB | :8080 | 用户认证服务 |
| redis | 16.3MB | :6379 | 缓存 |

#### 问题 & 解决方案

**问题1：CUDA 包导致镜像过大（9.42GB）**

现象：`easyocr` → `torch` → 自动拉 Linux CUDA 版，nvidia-* 包合计 ~2GB
根因：pip 默认 torch wheel 含 CUDA 支持，容器用不上
解决：Dockerfile 先装 CPU-only torch 再装 requirements.txt，pip 检测到 torch 已存在跳过 CUDA 版
效果：镜像从 9.42GB 降至 2.82GB，构建耗时从 20min 降至 5min

**问题2：HuggingFace 模型国内无法下载**

现象：Docker 构建时 `from fastembed import TextEmbedding` 下载模型失败
根因：
- `paraphrase-multilingual-MiniLM-L12-v2` 和 `jinaai/jina-embeddings-v3` 均用 XetHub 存储
- 国内镜像站 `hf-mirror.com` 返回 401（无法代理 XetHub 鉴权）
解决：去掉模型预下载步骤，接受 BM25 关键词搜索降级
后续：若想恢复语义搜索，可在有外网环境手动下载模型后 COPY 进镜像，或用 LLM API 嵌入

**问题3：auth-service 数据库缺列（token_version）**

现象：登录报 500 `no such column: users.token_version`
根因：auth-service 首次启动时 `Base.metadata.create_all()` 未创建该列（模型版本不一致）
解决：手动 ALTER TABLE 添加列 + 在 `main.py` 中加入 `_ensure_columns()` 自动迁移
效果：已修复，后续构建不会复现

**问题4：nginx 反向代理 405**

现象：`{"detail":"Method Not Allowed"}` 显示在浏览器
根因：`/api/admin/users` 被 nginx 转发到 app（不含用户管理路由），auth-service 有该路由
解决：nginx 增加 `location /api/admin/users` 转发到 auth-service
效果：所有 API 端点正常返回 200

**问题5：用户从 localhost:8000 访问导致 405**

现象：用户习惯访问 `http://localhost:8000`（app 直连口），没有 auth 路由
根因：docker-compose.yml 暴露了 `8000:8000`，用户绕过 nginx
解决：屏蔽 app 的 8000 端口映射，强制走 nginx（`:80`）

### 2026-07-13：OCR 提示词修复 + 清理 fix_prompt.py

#### 背景

在开发 OCR 服务（`ocr_service.py`）时，LLM Vision 的日语提取提示词因手误导致 Python 语法错误（字符串内的引号冲突），文件无法编译。

#### 解决方案

创建 `fix_prompt.py` 作为一次性修复脚本：
- 通过字符串匹配定位到坏掉的提示词区域
- 用正确的提示词整体替换
- 末尾用 `py_compile.compile()` 验证语法修复成功

#### 后续清理

修复完成后删除 `fix_prompt.py`，避免遗留无用脚本。该脚本的核心价值（定位坏串 → 替换 → 语法校验）已记录在此日志中，供日后参考。
